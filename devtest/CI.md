# The suite on GitHub

`.github/workflows/emulators.yml` builds the x86_64 debug APK once and runs the full suite (what `EVERYWHERE=1 bash devtest/all.sh` runs on the PC) on Android 10 to 16, one GitHub machine per version, all at the same time.

- Start: Actions > Emulators > Run workflow (pick a version or all), or `gh workflow run emulators.yml --ref <branch> -f version=all`. The workflow file must be on the default branch for that. A push to `ci-emulators` or `devtest-no-flake` also starts it (one version, or `[avds: afg14 msd29]` / `[avds: all]` in the commit message).
- Results: the table per version is in the run's summary page. Per version the artifact `results-<avd>` holds `devtest-out/` (results.txt, log, pictures) as a .tgz. Artifacts are kept 3 days.
- Duration: see the table (minutes) of the last run.
- On a runner the suite uses `devtest/linux.sh` (start and stop of the emulator), AVDs from `devtest/ci/make_avd.sh`, and `devtest/ci/run.sh`. Windows behaviour is unchanged.
- Known SDK bug (mobile-sentinel 0.7.0, `run_gradle` in build_sentinel.rs): it starts the relative path `target/sentinel-android/gradlew` with that folder as working directory, which fails on Linux ("No such file"). The workflow works around it with a symlink; the SDK should use an absolute path.

- Options per version, joined by `+`: `msd30+default` (AOSP image without Google APIs), `afg15+c2` / `c3` (2 or 3 emulator cores instead of 4). Used in the push commit message: `[avds: afg15 msd30+default]`.
- Each job also writes `host_load.txt` (load and free memory every 15 s) into its results; a failed scenario has `<name>.anr.txt` (system stack dumps) and `<name>.audio.txt` (audio server state).
- Asking again: a scenario that repeats a step (a lost touch, a machine that used a limit up) calls `retry_used` (lib.sh). Its PASS line says `(ASKED AGAIN: ...)` with the host load against the cores at that moment; the job summary lists every use, and a use on a machine that was not starved (load below the cores) is a FINDING that fails the job. s22b does not ask again: its purpose is that one hold ends the alarm.

## Only some scenarios, and sabotage mode

- Only some scenarios: the input `scenarios` of the manual run (names with spaces between, empty means all), or `[only: s50 s53]` in the commit message of a push. They are the names `devtest/one.sh` and `matrix.sh` take. The job runs only these on every version (`SCENARIOS` in `tiers.sh`; `devtest/ci/run.sh` stops at once on a name that is no scenario) and the summary says so. A commit message with `[only: ...]` that gives no name fails the first job instead of running everything; a version token with anything but letters, digits and `+` is dropped.
- Sabotage mode: the input `chaos` (yes or no), or `[chaos]` in the commit message. It sets `CHAOS=1`, which `devtest/chaos.sh` (sourced by `lib.sh`) turns into: 30% of the real touches (`input tap`, `swipe`, `touchscreen`, `draganddrop`, from helpers and scenarios alike) are not sent, a touch that is sent waits 0 to 1.5 s first, every `ui` command waits 0 to 0.3 s, and 2 busy loops run inside the emulator for the whole run (only on an emulator, never on a phone). Keys and typed text are never dropped. The numbers can be changed with `CHAOS_DROP` (percent), `CHAOS_TOUCH_MS`, `CHAOS_STEP_MS`, `CHAOS_HOG` and `CHAOS_SEED` (a number; unset: one is chosen and printed at the start of the log). The same seed with the same order of calls decides the same.
- What it leaves: `chaos.txt` in the results of the version (one line per dropped touch: scenario and command), `chaos.state` (seed, touches sent, touches dropped), a line at the end of the log, and a line in the job summary: `Sabotage on: seed N, touches sent X, touches dropped Y`. Without `CHAOS=1` nothing of this exists and the suite behaves as before. A scenario that asks again (`retry_used`) on a machine that is not starved still fails the job, also under sabotage.
- Locally: `CHAOS=1 CHAOS_SEED=7 bash devtest/one.sh afg16 5554 s50`. The mode itself is tested without a device: `bash devtest/chaos.test.sh`.
- The lint: `bash devtest/lint.sh [--report] [--list]` counts what the scenario files may not hold (`sleep`, raw `input`, `uiautomator`, hand-made retries; `# lint-ok: <reason>` allows a line). `--report` always exits 0, without it a count above zero exits 1. Its own cases: `bash devtest/lint.test.sh`.

## The device before each scenario, and INFRA

- `devtest/baseline.sh` (sourced by `lib.sh`; the runner of `matrix.sh` goes through `run_unit`): before each scenario one call to the device reads the keyboard, a PIN, the lock screen, the screen, the focus (the app or a launcher is a baseline, the shade, Settings, a picker, Recents or a not-responding dialog are not), screen size and density, font scale, forced Doze, automatic time, time zone, rotation, night mode, screen timeout and stay-awake. What is off is put back with the command the suite already has, read again, and written as `NOTE  <scenario>  the scenario before (<name>) left: ... (put back)`; that is a finding about the scenario before. After a put-back it waits a second before reading again (a change of focus, the keyboard and the shade show late in the dumps), up to four rounds; what is still off is INFRA and the scenario does not run. The start of a run clears a PIN that a killed run left before the first reading. On a phone nothing is changed: a NOTE says what changed. Every reading is a line in `baseline.txt` of the results; `BASELINE  not readable on this device` in the log names a value that this Android version does not print (it is then left out).
- The watchdog: the process id of `system_server` and of `audioserver` and the boot id are remembered from that reading and read again after the scenario, pass or fail, together with the log of the system (a crash of either). A change, a new boot or a crash is the device breaking: the scenario's own lines become `INFRA  <scenario>  [..s] <what broke>; the scenario said: ... [rerun follows]`, the device is restarted (`reboot_and_wait`) and the scenario runs once more; the second run is the one that counts, both stay in `results.txt`. Broken again: the INFRA line has no `[rerun follows]` and stands. A restart that a scenario means (s11, s13) is announced by `reboot_only` (`watchdog_announce_restart`), and when the device is back the new processes are remembered again (`watchdog_rebase`), so a break later in the same scenario still counts. The crash scan reads the log buffers as they are: `scenario()` clears them with `logcat -c` at its start and a restart empties them, so only lines of this scenario are in them (`baseline.test.sh` checks that `scenario()` still clears). A process of the app that dies is never looked at: that is a FAIL. The log of the system is kept as `<scenario>.infra.log`. A second run starts without the bash variables the first one left (`unit_forget`: the retry counters, the s13d mark, extra alarm fields).
- Exit code of a run (`matrix.sh`, `all.sh`, `ci/run.sh`): 1 when any FAIL (or an incomplete run), else 4 when an INFRA stands, else 0. The job summary lists INFRA lines apart under "The device broke".
- Proof on a device: `SCENARIOS="t01_leftovers t02_after_leftovers t03_device_breaks t04_app_dies"` (`devtest/selftest.sh`; `[only: t01_leftovers t02_after_leftovers t03_device_breaks t04_app_dies]` in a commit message): t01 leaves a font scale, a screen size and the keyboard; t02 must start clean and carry three NOTE lines; t03 kills `system_server`, its first result must be INFRA and the second PASS; t04 kills the app and must never be INFRA. Without a device: `bash devtest/baseline.test.sh`.
