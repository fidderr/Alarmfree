# The suite on GitHub

`.github/workflows/emulators.yml` builds the x86_64 debug APK once and runs the full suite (what `EVERYWHERE=1 bash devtest/all.sh` runs on the PC) on Android 10 to 16, one GitHub machine per version, all at the same time.

- Two parts per version: a full run is 14 jobs (seven versions, part 1 and 2 each, a fresh emulator per part; 20 jobs may run at once on the account, 6 stay free for other runs). `devtest/ci/split.py` deals the units of the full list (`ALL` in matrix.sh) out by their expected seconds from `devtest/ci/durations.txt` (biggest first to the lighter part; each part keeps the order of the list, `big_screens` first, the restarts with a PIN last; a unit that is not in the file weighs 60 s). The self-test checks that every unit is in exactly one part and that the parts differ by less than 10%: `bash devtest/split.test.sh`. Refresh the file from a full run: `python3 devtest/ci/split.py --measure <unit_times.txt of the results...>` (every run writes `unit_times.txt`: seconds per unit). A run of only some scenarios (`[only: ...]`) is one part. Results are `results-<avd>-<part>`; the last job (`summary`, `devtest/ci/merge.sh`) merges the parts into one table per version (passed, flaky, failed, INFRA, skipped, slowest part) and prints the gate line.
- The release gate: a full run with 0 FAIL, 0 INFRA and 0 FLAKY on all seven versions, every part present (the `GATE:` line of the summary).
- FLAKY: a scenario that FAILs runs once more on the same emulator (no restart). A pass on the rerun is one `FLAKY` line with both results (kept apart in the summary; the first failure's files are copied to `first_<file>` before the rerun can write over them), a second FAIL stays one FAIL (`failed twice; first run: ...`), INFRA keeps its own path (restart and rerun). A FLAKY does not fail the job; it is a finding to investigate, and the gate counts it. `FLAKY_RERUN=0` turns the rerun off. Cases: `baseline.test.sh` (`r_flaky*`).
- New or changed scenarios join the full list only after 10 runs in a row on msd30 (`[avds: msd30] [only: sX sX sX sX sX sX sX sX sX sX]`) with no FAIL and no FLAKY.
- Start: Actions > Emulators > Run workflow (pick a version or all), or `gh workflow run emulators.yml --ref <branch> -f version=all`. The workflow file must be on the default branch for that. A push to `ci-emulators` or `devtest-no-flake` also starts it (one version, or `[avds: afg14 msd29]` / `[avds: all]` in the commit message).
- Results: the table per version is in the run's summary page. Per version the artifact `results-<avd>` holds `devtest-out/` (results.txt, log, pictures) as a .tgz. Artifacts are kept 3 days.
- Duration: see the table (minutes) of the last run.
- On a runner the suite uses `devtest/linux.sh` (start and stop of the emulator), AVDs from `devtest/ci/make_avd.sh`, and `devtest/ci/run.sh`. Windows behaviour is unchanged.
- Known SDK bug (mobile-sentinel 0.7.0, `run_gradle` in build_sentinel.rs): it starts the relative path `target/sentinel-android/gradlew` with that folder as working directory, which fails on Linux ("No such file"). The workflow works around it with a symlink; the SDK should use an absolute path.

- Options per version, joined by `+`: `msd30+default` (AOSP image without Google APIs), `afg15+c2` / `c3` (2 or 3 emulator cores instead of 4). Used in the push commit message: `[avds: afg15 msd30+default]`.
- Each job also writes `host_load.txt` (load and free memory every 15 s) into its results; a failed scenario has `<name>.anr.txt` (system stack dumps) and `<name>.audio.txt` (audio server state).
- Asking again: a scenario that repeats a step (a lost touch, a machine that used a limit up) calls `retry_used` (lib.sh). Its PASS line says `(ASKED AGAIN: ...)` with the host load against the cores at that moment; the job summary lists every use, and a use on a machine that was not starved (load below the cores) is a FINDING that fails the job. s22b does not ask again: its purpose is that one hold ends the alarm.

## Only some scenarios, and sabotage mode

- Only some scenarios: the input `scenarios` of the manual run (names with spaces between, empty means all), or `[only: s50 s53]` in the commit message of a push. They are the names `devtest/one.sh` and `matrix.sh` take. The job runs only these on every version (`SCENARIOS` in `tiers.sh`; `devtest/ci/run.sh` stops at once on a name that is no scenario) and the summary says so. A commit message with `[only: ...]` that gives no name fails the first job instead of running everything; a version token with anything but letters, digits and `+` is dropped.
- Sabotage mode: the input `chaos` (yes or no), or `[chaos]` in the commit message. It sets `CHAOS=1`, which `devtest/chaos.sh` (sourced by `lib.sh`) turns into: 30% of the real touches (`input tap`, `swipe`, `touchscreen`, `draganddrop`, from helpers and scenarios alike) are not sent, a touch that is sent waits 0 to 1.5 s first, every `ui` command waits 0 to 0.3 s, and 2 busy loops run inside the emulator for the whole run (only on an emulator, never on a phone). Keys and typed text are never dropped. The numbers can be changed with `CHAOS_DROP` (percent), `CHAOS_TOUCH_MS`, `CHAOS_STEP_MS`, `CHAOS_HOG` and `CHAOS_SEED` (a number; unset: one is chosen and printed at the start of the log). The same seed with the same order of calls decides the same.
- What it leaves: `chaos.txt` in the results of the version (one line per dropped touch: scenario and command), `chaos.state` (seed, touches sent, touches dropped), a line at the end of the log, and a line in the job summary: `Sabotage on: seed N, touches sent X, touches dropped Y`. Without `CHAOS=1` nothing of this exists and the suite behaves as before. A scenario that asks again (`retry_used`) on a machine that is not starved still fails the job, also under sabotage.
- Locally: `CHAOS=1 CHAOS_SEED=7 bash devtest/one.sh afg16 5554 s50`. The mode itself is tested without a device: `bash devtest/chaos.test.sh`.
- The lint: `bash devtest/lint.sh [--report] [--list]` counts what the scenario files may not hold (`sleep`, raw `input`, `uiautomator`, hand-made retries; `# lint-ok: <reason>` allows a line). Also `sleep-check`: a fixed sleep directly before a line that reads the screen or the app (`texts_of`, `sn`, `ui`, `state`, `is_there`, `case`, `if`, `[ ]`); the hits that existed are in `devtest/lint_sleep_check.txt`, which only shrinks (a new hit or an entry that no longer hits fails the lint). `--report` always exits 0, without it a count above zero exits 1. Its own cases: `bash devtest/lint.test.sh`.

## The device before each scenario, and INFRA

- `devtest/baseline.sh` (sourced by `lib.sh`; the runner of `matrix.sh` goes through `run_unit`): before each scenario one call to the device reads the keyboard, a PIN, the lock screen, the screen, the focus (the app or a launcher is a baseline, the shade, Settings, a picker, Recents or a not-responding dialog are not), screen size and density, font scale, forced Doze, automatic time, time zone, rotation, night mode, screen timeout and stay-awake. What is off is put back with the command the suite already has, read again, and written as `NOTE  <scenario>  the scenario before (<name>) left: ... (put back)`; that is a finding about the scenario before. After a put-back it waits a second before reading again (a change of focus, the keyboard and the shade show late in the dumps), up to four rounds; what is still off is INFRA and the scenario does not run. The start of a run clears a PIN that a killed run left before the first reading. On a phone nothing is changed: a NOTE says what changed. Every reading is a line in `baseline.txt` of the results; `BASELINE  not readable on this device` in the log names a value that this Android version does not print (it is then left out).
- The watchdog: the process id of `system_server` and of `audioserver` and the boot id are remembered from that reading and read again after the scenario, pass or fail, together with the log of the system (a crash of either). A change, a new boot or a crash is the device breaking: the scenario's own lines become `INFRA  <scenario>  [..s] <what broke>; the scenario said: ... [rerun follows]`, the device is restarted (`reboot_and_wait`) and the scenario runs once more; the second run is the one that counts, both stay in `results.txt`. Broken again: the INFRA line has no `[rerun follows]` and stands. A restart that a scenario means (s11, s13) is announced by `reboot_only` (`watchdog_announce_restart`), and when the device is back the new processes are remembered again (`watchdog_rebase`), so a break later in the same scenario still counts. The crash scan reads the log buffers as they are: `scenario()` clears them with `logcat -c` at its start and a restart empties them, so only lines of this scenario are in them (`baseline.test.sh` checks that `scenario()` still clears). A process of the app that dies is never looked at: that is a FAIL. The log of the system is kept as `<scenario>.infra.log`. A second run starts without the bash variables the first one left (`unit_forget`: the retry counters, the s13d mark, extra alarm fields). One break is known and is not INFRA the first time (`KNOWN_FAULT_<unit>` in `baseline.sh`, only s53): on the Android 11 image `system_server` crashes in its own code (a SecurityException binding the permission controller's `RoleControllerService`) while the settings screen of the "Stay allowed when unused" fix button opens; when the log holds exactly that text the first run becomes one `NOTE  s53  the first run met a known fault of this device image (...)`, the device is restarted and the second run counts; the same break again is INFRA and stands.
- The connection to the device (GitHub machines only, or `LINK_WATCH=1`): while a unit runs, a poller writes every 2 s in which `adb get-state` is not `device` into `<unit>.link.txt`, and `adb_` adds the lines adb itself printed (`device offline`, `waiting for device`, `device '...' not found`). The emulator can drop off adb for half a minute with the guest untouched (run 45191082131, afg15: s25@1600x2560 and s49@2208x1840; load and free memory of the machine were the same as on the versions that never dropped). A scenario that FAILED while the connection was down (and no restart was meant) is not a FAIL: the first run becomes `NOTE  <unit>  the first run lost the connection to the device (adb: ...)`, the runner waits for the connection (`link_restore`: `adb wait-for-device`, new shells; no restart) and runs the unit again; the second run counts, and a second drop is INFRA that stands (exit 4). A scenario that passed keeps its PASS and gets one NOTE. After a scenario the watchdog that gets no answer waits for the connection once and asks again before it calls the device broken. Cases: `baseline.test.sh` (`r_link*`, the `adb_` hook, `kf_size`).
- A device that stops answering (run 45231328491, msd29, s26: no answer to `adb shell` for 90 minutes until the job was cancelled): when the open shell does not answer within `ASK_TIMEOUT` and `adb shell echo ok` does not either, `device_dead_check` writes the flag file (`DEAD_FILE`) and every later `dev`, `as_app`, `ask` and `adb_` call fails at once (124, no output) until `open_shells` or `reboot_only` runs; `await_sound` and `await_silence` give up when the device gives no clock three times in a row. The scenario then ends in seconds, the watchdog gets no answer (after one wait for the connection) and the unit is INFRA with one restart and one rerun. Cases: `devtest/dead.test.sh`.
- Exit code of a run (`matrix.sh`, `all.sh`, `ci/run.sh`): 1 when any FAIL (or an incomplete run), else 4 when an INFRA stands, else 0. The job summary lists INFRA lines apart under "The device broke".
- Proof on a device: `SCENARIOS="t01_leftovers t02_after_leftovers t03_device_breaks t04_app_dies"` (`devtest/selftest.sh`; `[only: t01_leftovers t02_after_leftovers t03_device_breaks t04_app_dies]` in a commit message): t01 leaves a font scale, a screen size and the keyboard; t02 must start clean and carry three NOTE lines; t03 kills `system_server`, its first result must be INFRA and the second PASS; t04 kills the app and must never be INFRA. Without a device: `bash devtest/baseline.test.sh`.

## Android's own screens (devtest/system.sh)

The lock screen and its PIN pad, the shade, the file picker, the launcher's widget dialog and the pages of Android's Settings are not the app's window, so the app cannot say what is on them. `devtest/system.sh` (sourced by `lib.sh`) reads them from the device and every step follows one rule: wait for a named state read from the device (`sys_wait SECONDS "what" check...`, deadline 30 s, a failure says which state did not come and what the device showed), act once, confirm with a read, and act again only when a read proves the first action did nothing. Reads: `uiautomator dump` through `sys_dump` and `devtest/sys_nodes.py` (it works on the lock screen, the shade and the picker on Android 10 to 16), `dumpsys window` for the focus and the lock screen (`kg_state`), `dumpsys activity service com.android.systemui` for the shade (`shade_state`), `dumpsys input_method` for the keyboard.
- PIN: `unlock_pin` waits for the pad (`pinEntry` with the focus), types the PIN once, reads back one bullet per digit, presses Enter once, and waits for the user unlocked and the lock screen gone. A wrong PIN is then a finding, not a typing accident (the cause of "Wrong PIN" on Android 14 was a second blind try at a field that had lost the focus).
- SDK unlock screen: `sdk_unlock_press` (the button's place from the tree, one touch, the SDK's own log line "quiet for the unlock" or the focus leaving as the confirmation), `sdk_unlock_cancel`, `home_from_unlock` (Home does nothing on Android 12 and 16 over a locked phone: a NOTE, not a failure).
- Shade: `shade_set open|closed` (`cmd statusbar expand-notifications|collapse`, read back, asked again only while the read says it is not there), `tap_in_shade Skip|Undo`.
- File picker: `picker_pick name`: Show roots, Downloads, then the file; Google's picker (Android 12 to 16) only previews a file on a touch, so the keys choose it; Android 10 and 11 take the touch. Every step is in `picker_trace.txt` of the results.
- Lock screen after `locksettings clear`: `lock_away` (`wm dismiss-keyguard` on Android 13 to 16; sleep, wake and dismiss on Android 10 to 12), also used by the baseline of the runner; `lock_away.txt` says which step worked.
- A not-responding dialog of Android in front (System UI after a boot on Android 15) is put away with its Wait button inside every `sys_wait` (a NOTE says so); one of the app's own is a failure.
- `probe.sh` (by name only: `t05_probe_lock t06_probe_shade t07_probe_picker`) writes what the device says for these screens into `probe_*.txt`.
